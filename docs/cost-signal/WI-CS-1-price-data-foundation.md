# WI-CS-1 — Price data foundation: `fdc_food_price` table + seed

## Background

The cost-to-make signal (see `docs/cost-signal/DESIGN.md`) needs a US national-average grocery
price for each FNDDS food. USDA ERS **Purchase to Plate National Average Prices (PP-NAP)** provides
exactly this: a public-domain CSV of `price_100gm` (USD per 100 edible grams) keyed to the 8-digit
FNDDS/WWEIA `food_code`. The app already seeds the FNDDS nutrition catalog the same way — a one-off
offline script (`server/scripts/build-fdc-catalog.ts`) that reads a large source file and batch-inserts
into `fdc_foods` / `fdc_food_nutrient`, and a derived catalog (`build-allergen-catalog.ts` →
`fdc_food_allergen`) keyed to `fdc_id`. This work item adds the price table on the same pattern.

The one wrinkle: `fdc_foods` is keyed by `fdc_id`, but PP-NAP is keyed by `food_code`. The current
FNDDS seed reads only `fdcId` from the Survey JSON (`SurveyFood` interface in `build-fdc-catalog.ts`,
lines 27–33). The price seed must build the `food_code → fdc_id` join itself.

**PP-NAP source:** `pp_national_average_prices_csv.zip` from
https://www.ers.usda.gov/data-products/purchase-to-plate — key columns `food_code`, `price_100gm`,
`method`, `method_description`. Public domain; no caching/redistribution restriction. Neither this CSV
nor the 66 MB FNDDS JSON is committed to the repo (same as the nutrition source).

## Objective

Add an `fdc_food_price` table and a one-off, idempotent seed script `build-ingredient-prices.ts` that
joins PP-NAP `food_code` to the seeded `fdc_foods.fdc_id` and populates the table. Add the two new
`recipes` columns the compute step (WI-CS-2) will write. Ship a small price fixture so downstream work
can test offline. No runtime code and no workflow changes here — this is the data substrate only.

## Acceptance Criteria

1. **Schema.** Given the migration is applied, when the DB is inspected, then table `fdc_food_price`
   exists with columns `fdc_id` (integer, pk, fk → `fdc_foods.fdc_id`), `food_code` (text, not null),
   `price_per_100g` (text, not null), `method` (text, nullable), `source_cycle` (text, not null) —
   matching `src/schema.ts` conventions (numeric-as-text, `static`-style table def).
2. **Recipe columns.** Given the migration is applied, then `recipes` has nullable
   `cost_per_serving_cents` (integer) and `cost_coverage` (text). Additive and backwards-compatible:
   old code runs unchanged against the new schema.
3. **Migration hygiene.** The migration is generated by `drizzle-kit generate` (never hand-DDL), and
   the two table changes are split if generation would otherwise prompt (per the destructive+additive
   staging principle in `harvest-principles.md`). Additive-only here, so one migration is expected.
4. **`food_code → fdc_id` join (resolves Q-01).** Given a PP-NAP row with `food_code` F and an FNDDS
   food whose `foodCode` is F, when the seed runs, then one `fdc_food_price` row is written with that
   food's `fdc_id` and the row's `price_100gm` stored verbatim as `price_per_100g`. If a `food_code` has
   no matching FNDDS food, the row is skipped (logged count), never guessed.
5. **Idempotent + batched.** Given the seed runs twice, then the second run inserts nothing new
   (`onConflictDoNothing`), and inserts are batched at 500 rows — mirroring `insertFdcFoods`.
6. **Lowest-granularity storage.** `price_per_100g` stores the **raw** 2017–18 value (no CPI applied,
   no cents rounding) so re-inflation or a newer cycle rebuilds without re-sourcing.
7. **Fixture.** A `pp-nap.fixture.ts` (or additions to `fdc-foods.fixture.ts`) seeds prices for at least
   flour, chicken, olive oil, and one deliberately **unpriced** fixture food, reusable by WI-CS-2 tests.

## Test Cases

### Test Case 1: Migration creates the price table and recipe columns (AC 1, 2, 3)

**Preconditions:** Clean `migratedFileDb()`.
**Steps:** Apply all migrations. Query `PRAGMA table_info(fdc_food_price)` and `PRAGMA table_info(recipes)`.
**Expected Outcomes:** `fdc_food_price` has the five columns with the stated types/constraints;
`recipes` includes `cost_per_serving_cents` (integer, nullable) and `cost_coverage` (text, nullable).
An existing recipe-insert test still passes (backwards-compatible).

### Test Case 2: Seed joins food_code → fdc_id and stores raw price (AC 4, 6)

**Preconditions:** `migratedFileDb()` seeded with a 3-food FNDDS fixture whose foods carry known
`fdc_id` and `food_code`. A 4-row PP-NAP fixture: 3 codes matching the FNDDS foods, 1 code matching none.
**Steps:** Run the seed's pure mapping + insert against the fixture DB.
**Expected Outcomes:** Exactly 3 `fdc_food_price` rows; each `fdc_id` matches the FNDDS food whose
`food_code` equals the PP-NAP `food_code`; `price_per_100g` equals the fixture's raw `price_100gm`
string (unmodified); the unmatched code produces no row and is counted in the skip log.

### Test Case 3: Seed is idempotent (AC 5)

**Preconditions:** As Test Case 2, after one seed run.
**Steps:** Run the seed a second time. Count rows.
**Expected Outcomes:** Row count unchanged; no error.

### Test Case 4: Q-01 verification against real data (AC 4)

**Preconditions:** Access to the real FNDDS Survey JSON (`FNDDS_JSON`).
**Steps:** Before writing the join, inspect one Survey food object for a top-level `foodCode` field.
**Expected Outcomes:** If present, the seed reads `food.foodCode` directly. If absent
`[ASSUMPTION: foodCode is present on FDC Survey foods]`, fall back to the FNDDS "At A Glance" ingredient
files or the FDC API to build the `fdc_id ↔ food_code` map, and document the choice in the script header.

## Deployment Strategy

Direct deploy, staged: (1) `npm run db:generate` → review the generated `.sql` by hand → `npm run
db:migrate`; (2) run `tsx server/scripts/build-ingredient-prices.ts` once against Turso **after**
`build-fdc-catalog.ts` has populated `fdc_foods`. Additive/nullable schema and an idempotent seed mean
no rollback is needed — the table and columns are inert until WI-CS-2 reads them. Operator must supply
the PP-NAP CSV path and the FNDDS JSON path via env, exactly as the nutrition seed takes `FNDDS_JSON`.

## Production Verification

### Production Verification 1: Price table populated and joinable

**Preconditions:** Migration applied and seed run against the production Turso DB.
**Steps:** `SELECT count(*) FROM fdc_food_price;` and a spot join
`SELECT f.description, p.price_per_100g FROM fdc_food_price p JOIN fdc_foods f USING (fdc_id) WHERE
f.description_normalized LIKE '%flour%' LIMIT 5;`.
**Expected Outcomes:** Non-trivial row count (thousands); flour returns a plausible sub-dollar
`price_per_100g`; the join returns rows (confirms `fdc_id` keys align with the catalog).
