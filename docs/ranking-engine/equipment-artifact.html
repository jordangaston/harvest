Harvest · Ranking Engine · Signal #9

Kitchen Equipment

Detect the appliances each recipe step needs, then filter the deck by what's actually in the user's kitchen. The third hard filter — no weight, it gates the pool.

3rd hard filter LLM-primary detection per-recipe essentiality extends DESIGN.md
The rule — a reviewed user, per detected appliance
exclude ← required equipment they don't own (non-substitutable: sous-vide, smoker)
−0.10 ← recommended equipment they don't own (substitutable: air-fryer → oven)
keep ← owned · or the recipe needs only baseline gear · or detection unknown

Two halves

Detect at import, filter at rank

A · Detection (import)

A new capability on the import pipeline: read each recipe and determine the notable appliances its steps need — including ones only implied by context — and whether each is essential or merely convenient for that recipe.

B · Filter (rank)

An EquipmentFilter joins the engine's existing hard-filter registry (alongside allergens and diets). One array entry — no engine rewrite. Required-missing excludes; recommended-missing softly penalizes.

Only notable appliances are tracked (a controlled vocab: air fryer, slow cooker, pressure cooker, sous-vide, smoker, stand mixer, blender, …). Baseline gear — oven, stovetop, knives, pans — is assumed present and never filtered.

Detection · LLM-primary, deterministic fallback

Why this needs an LLM

Equipment is often implicit and substitution is a judgment. A recipe titled "Air Fryer Wings" whose steps only say "cook at 400°F for 12 min" names no appliance in any step; "beat to stiff peaks" implies an electric mixer. And whether an air-fryer recipe survives in an oven is reasoning, not a keyword. A keyword matcher is a high-precision / low-recall floor — not a primary.
primary

Recipe-analysis LLM

Its own pipeline step (EquipmentDetector) with a single-purpose prompt reading title + ingredients + steps. Returns equipment constrained to the vocab — including implicit gear — with a per-recipe essentiality (required / recommended), an optional substitute note, and per-step alignment for the UI.

↓ on failure / timeout
fallback

Alias matcher (deterministic)

Word-boundary scan over step text catches explicit mentions only, using the per-type defaultEssentiality prior — and sets equipment_complete = false so the filter stays lenient. Tiered fallback: emit something rather than nothing, but don't hard-exclude on uncertain data.

Pipeline: … → categorize → equipment → diet → persist — its own step. Best-effort like every other enrichment step; never fails the import.

The gate · essentiality × ownership

Required excludes, recommended penalizes

Essentiality is the allergen-severity / diet-strictness analog — judged per recipe by the LLM (slow-cooking as the method vs. a convenience), stored on recipe_equipment. The config default is only the fallback prior.

Recipe needs…User owns itUser lacks it
required non-substitutable keep exclude
recommended substitutable keep keep · −0.10
baseline oven/stovetop/knife not tracked not tracked

Gated on review

The filter engages only when equipment_reviewed = true — a flag set when the user reviews their kitchen (even if they own nothing). This distinguishes "owns nothing special" from "hasn't told us," so we never hide recipes from a user who simply hasn't set up. Same stance as allergens: no data → no filter.

Lenient on unknowns

A recipe with equipment_complete = false (imported before this feature, or an LLM miss) is treated as unknown and kept — over-filtering hides good food, and hiding a dish because the model hallucinated a smoker is the failure mode to guard against (Q-E6). Safe to ship before any backfill.

Decisions & open questions

What's settled, what isn't

✓ LLM-primary detection
First draft chose keyword-primary; corrected — it misses implicit gear and can't reason about substitutes. Keyword scan is the fallback.
✓ Per-recipe essentiality
Stored on recipe_equipment; substitutability is a recipe-level judgment, not a fixed appliance property.
✓ Hard filter, no weight
You can't "mostly" own an air fryer — absence is binary. Gates like allergens/diet.
✓ Dedicated detection step
Its own EquipmentDetector LLM call with a single-purpose prompt — not folded into the categorizer — for cleaner quality and independent retries.
Q-E6 · detection accuracy
We're trusting an LLM to drive a hard exclude. Needs a labeled eval set before leaning on it — start lenient, watch equipment_filtered_ratio.
Q-E1 · where users declare
Onboarding vs settings vs inferred. Data model is ready either way.
